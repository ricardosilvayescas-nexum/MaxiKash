01 · Alineación de Capas

Separación de responsabilidades

Para garantizar que cada equipo mantenga autonomía en su tecnología sin romper el contrato de datos, se establece la frontera formal entre la base de datos y la capa de aplicación:

CapaResponsableConvención / Alcance
Modelo físico (BD, tablas, columnas, SPs)Data Engineeringsnake_case, español técnico. Acceso solo vía SPs o vistas.
Acceso a datos / ORM / DTOsBack-EndLibre elección (camelCase / DTOs). Mapea UUIDs y firma de SPs.
Contratos de API (JSON)Back-EndExpone exclusivamente uuid_externo — nunca IDs numéricos.
Consumo de la APIFront-End / MóvilSin interacción directa con la base de datos. Consumo REST/gRPC.

El identificador uuid_externo actúa como el desacoplamiento clave: la base maneja autoincrementables eficientes internamente, mientras Back-End expone identificadores seguros y universales en sus APIs.

03 · Estructura Base de Tabla

Identificador público y auditoría

Cada tabla de negocio tiene dos llaves con propósitos distintos: id_<entidad> es la llave interna, autoincremental, de uso exclusivo de la base de datos — nunca se expone fuera de ella. uuid_externo es el identificador público: lo genera la propia base al insertar (no la aplicación) y es el único que Back-End/Front-End deben consumir.

Adicionalmente, toda tabla de negocio incluye trazabilidad obligatoria de creación y modificación (creado_por / actualizado_por).

fragmento real — tablas/01_pilot_schema_naming.sql
CREATE TABLE usuarios (
    id_usuario          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,        -- interna, nunca se expone
    uuid_externo        CHAR(36)     NOT NULL DEFAULT (UUID()),          -- publica, la genera la base
    ...
    creado_por          VARCHAR(80)  NULL,   -- usuario/servicio ejecutor
    actualizado_por     VARCHAR(80)  NULL,   -- usuario/servicio del ultimo cambio
    fecha_creacion      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    fecha_actualizacion DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT uq_usuarios_uuid_externo UNIQUE (uuid_externo)
);
Ya aplicado

Las 6 tablas de negocio del piloto (usuarios, monederos, transacciones, creditos, pagos_credito, metodos_pago_usuario) ya tienen esta estructura corriendo en el ambiente de pruebas.

04 · Estandarización Físicas

Convenciones de nombrado

Toda entidad y objeto dentro de MySQL debe responder a reglas estrictas de lenguaje, prefijos y relaciones:

  • Idioma y formato: Español técnico en snake_case, minúsculas, sin acentos ni carácteres especiales (ñ).
  • Sustantivos: En plural para tablas de negocio (usuarios, monederos).
  • Motor: ENGINE=InnoDB siempre (soporta transacciones y FKs).

Prefijos de tablas

Tabla de negocio

tbl_usuarios, tbl_monederos
Catálogo / lookup

Tabla temporal

Staging / ETL

Nombres de campos y Llaves Foráneas

La PK de usuarios se llama id_usuario. Cualquier tabla que la referencie usa exactamente ese mismo nombre para su columna FK. Así se identifica la relación al instante:

ejemplo de relación FK
CREATE TABLE monederos (
    id_monedero  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    id_usuario   BIGINT UNSIGNED NOT NULL,  -- FK con el mismo nombre exacto de la PK de usuarios
    ...
    CONSTRAINT fk_monederos_usuarios FOREIGN KEY (id_usuario)
        REFERENCES usuarios (id_usuario)
);

05 · Interfaz de Programación

Arquetipos de procedimientos almacenados

Toda la lógica de escritura y procesos complejos pasa por Stored Procedures estandarizados bajo 5 plantillas principales:

Escritura · alta
sp_nucleo_ins_usuario
inserta y valida antes de escribir
Escritura · actualización
sp_monedero_upd_estatus
modifica un registro existente
Consulta
sp_nucleo_sel_usuario_by_correo
solo lectura, optimizada
Proceso de negocio
sp_monedero_proc_aplicar_deposito
transaccionalidad multi-tabla
ETL / Lotes
sp_etl_load_transacciones
cargas masivas en segundo plano

Los SPs de escritura responden con una firma unificada de 4 parámetros OUT para que Back-End interprete los resultados de manera transparente:

firma real — procedimientos_almacenados/04_sp_archetypes.sql
CREATE PROCEDURE sp_monedero_upd_estatus (
    IN  p_id_monedero      BIGINT UNSIGNED,
    IN  p_codigo_estatus   VARCHAR(30),
    IN  p_usuario_ejecutor VARCHAR(80),   -- audita quién solicita la acción
    OUT p_exito            TINYINT(1),    -- 1 = Exitoso, 0 = Error
    OUT p_codigo_salida    VARCHAR(30),   -- ej: MONEDERO_NO_EXISTE
    OUT p_mensaje          VARCHAR(150),
    OUT p_uuid_publico     VARCHAR(36)
)

Nota sobre carpetas reservadas

Las carpetas vistas/, funciones/, triggers/ y eventos/ existen desde ya para que todo objeto nuevo nazca ahí. Los objetos embebidos en el piloto original (como vw_saldos_monederos o el EVENT de drift) se mantienen en sus scripts históricos. Cada carpeta incluye un LEEME.md explicativo.

07 · Trazabilidad de Despliegues

Control de cambios por folio

Ningún cambio al esquema se ejecuta en producción o pruebas sin registrar antes un folio formal. Se rastrea la fecha, responsable, script aplicado y su reverso obligatorio.

10 · Evaluación de Impacto

Ventajas y retos de la propuesta

Para la toma de decisiones con Dirección de TI y Liderazgo de Desarrollo, se presenta el balance transparente entre el valor técnico aportado y la curva de adaptación operativa requerida:

Ventajas (Beneficio de Negocio y Técnico)Retos y Mitigación
Desacoplamiento Total: El uso de uuid_externo permite refactorizar la base interna o cambiar de motor sin romper las APIs de Back-End. Curva de Aprendizaje: El equipo debe acostumbrarse a no usar DELETE físico y pasar las modificaciones por SPs.
Mitigación: Arquetipos estándar listos para reutilizar.
Seguridad y Cumplimiento: Manejo explícito de datos sensibles (PII/PCI) y auditoría nativa sobre quién creó/modificó cada dato. Rigor en Despliegues: Requiere redactar y validar el script de reverso (rollback) por cada folio liberado.
Mitigación: Plantillas estructuradas en la carpeta reversos/.
Precisión Financiera: El uso obligatorio de DECIMAL(19,4) elimina descuadres o desbordamientos por redondeo de flotantes en saldos y pagos. Mayor número de objetos: Gestión de triggers, eventos y SPs adicionales.
Mitigación: Organización en repositorio estructurado en DBMAXI/.
Cero Despliegues Fallidos: El protocolo de Smoke Testing y la idempotencia garantizan estabilidad en los entornos de Pruebas y Producción. Gobernanza activa: Necesidad de monitoreo constante contra tablas huérfanas.
Mitigación: Detección automatizada vía Eventos MySQL y scripts DQL.
